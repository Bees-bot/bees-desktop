## Commands

```sh
npm ci                                              # postinstall also installs dsh-runtime deps and stages the @bees plugins
npm run check                                       # test:release + typecheck + npm test + vite build (the JS gate)
npm test                                            # build:dsh-client, then vitest run tests/dsh-*.test.ts
npx vitest run tests/dsh-product.test.ts            # one file (run `npm run build:dsh-client` first if it reads the client bundle)
npx vitest run tests/dsh-ui.test.ts -t "some name"  # one case
npm run typecheck
npm run prepare:dsh                                 # stage Node/Temporal/llama sidecars — required before cargo check/test
cargo check --manifest-path src-tauri/Cargo.toml
cargo test --manifest-path src-tauri/Cargo.toml --lib
make bees                                           # run the app against https://app.bees.bot (= make prod)
make dev                                            # run the app against http://localhost:3000 (needs `make server` in ../bees-server)
make build                                          # release installer (npm run tauri:build)
npm run release:prepare -- 0.2.1                    # version bump across npm/Tauri/Cargo + CHANGELOG heading
```

CI runs `npm run check`, then `npm run prepare:dsh`, `cargo check`, and `cargo test --lib`.

Gotchas: never run `npm run dev` beside `npm run tauri:dev` (Tauri owns port 1420 and calls `dev` itself). Fully quit Bees before switching `BEES_ACCOUNT_API_URL`, which is read once at startup. `dsh-runtime/plugin/lib/client.js` is generated by esbuild and gitignored.

This repo has a graphify hook: run `graphify query "<question>"` to orient before grepping the tree; grep for specific lines afterwards.

## Architecture

**The Tauri app is a launcher, not the product.** `src/entry.ts` is a splash page that invokes the `ensure_dsh_runtime` command. `src-tauri/src/lib.rs` starts a Temporal dev server and the bundled Node runtime (`dsh-runtime/start.mjs --profile bees --host 127.0.0.1 --port <stable>`), waits for `/healthz`, then navigates the webview to `http://127.0.0.1:<port>/bees-auth?token=<per-launch secret>`. Everything after that is the DSH web client. The Rust↔Node contract is entirely env vars (`BEES_DSH_TOKEN`, `BEES_DATABASE_PATH`, `BEES_DEFAULT_WORKSPACE`, `BEES_STATE_DIR`, `BEES_TEMPORAL_ADDRESS`, `BEES_RUNTIME_ROOT`, …). Rust also owns local model downloads and `llama-server` (`local_models.rs`) and sidecar reaping (`process.rs`).

**Bees ships as plugins inside a pinned DeepSeek Harness (DSH) host**, currently `0.1.5-rc.2`. `scripts/install-dsh-runtime.mjs` asserts that exact version and applies a small set of exact-match patches to the vendored DSH packages (startup timing, embedded UI content, one Agent Team model-routing bridge). Extend DSH through its plugin contracts; do not fork or widen those patches. Upgrades go through `docs/dsh-upgrade-checklist.md` as one tested set.

- `dsh-runtime/profile/cordis.patch.yml` is the Bees-owned profile overlay: it configures/disables upstream DSH plugins (sandbox policy, default model, subagent tools, `llm-pi-ai` providers) and inserts the `@bees/*` plugins. Which plugin is mounted, and with what config, is decided here — not in code.
- `dsh-runtime/plugin` is the product plugin (`@bees/dsh-plugin`): `lib/` is the Node side, `client/` is the browser UI. `lib/index.js` declares the DSH services it injects and registers the `/bees-api/*` routes on DSH's `webServer`; most mutations funnel through `/bees-api/command` → `executeProductCommand` (`lib/product-commands.js`).
- `dsh-runtime/plugins/{local-ai,free-ai,custom-ai,subscriptions}` are separate small DSH packages for AI connection options, injected into the client bundle as externals.
- `scripts/build-dsh-client.mjs` bundles `plugin/client/index.js` (React via local shims, one singleton) into `plugin/lib/client.js`. `scripts/stage-dsh-plugin.mjs` then **copies** each plugin into `dsh-runtime/node_modules/@bees/*`. Edits under `dsh-runtime/plugin` are invisible to the running app until re-staged; `scripts/prepare-desktop.mjs` (Tauri's `beforeDevCommand`/`beforeBuildCommand`) does the whole chain on each launch.

**Product data** lives in an app-owned SQLite file `bees-stage1.db`, opened with `node:sqlite` `DatabaseSync`. The core schema (users, teams, workspaces, processes, stages, work_items, agent assignments, locations) is in `lib/product-database.js`; feature modules create their own tables (`agent-runtime.js` for run queue/checkpoints/audit, `process-runtime.js`, `work-context.js`, `app-platform.js`). `BeesProduct` (`lib/product.js`) is the read/snapshot surface, `AgentRuntime` runs agent turns and recovery, `ProcessRuntime` drives durable multi-stage runs on Temporal, `Capabilities` (`lib/capabilities.js`) owns which MCP servers exist and which agents may use them — each enabled server becomes its own `dsh-mcp-client` fiber, secrets go to DSH's credential store.

**Data boundary** (non-negotiable, it is the product's premise): user-selected company folders are data-only. Inputs are staged into app-data workspaces and outputs are published only after approval in the UI. No database, session, index, checkpoint, browser profile, credential, or runtime metadata may be written into a mapped folder, and document contents are never uploaded anywhere.

## Tests

`tests/dsh-*.test.ts` are Vitest suites that import the plugin's `lib/*.js` directly and drive it against an in-memory SQLite database (`tests/node-database.ts`). UI suites assert against the client sources and the built bundle via `tests/client-source.ts` — which reads the client directory rather than a hand-maintained list, so a new `client/*.js` file is covered automatically. `tests/dsh-contract.test.ts` is the DSH upgrade gate (loopback auth, service injection, navigation contracts, workspace registration, approvals, durable restart, clean disposal); treat a failure there as a DSH integration problem, not a test to relax. `tests/release.test.mjs` and `tests/durable-temporal.integration.mjs` run under `node --test`.

## Conventions

- TypeScript (or plain ESM JS with `.d.ts` sidecars, as in `plugin/lib`) for business logic; Rust only where Tauri needs it. Match surrounding style; there is no separate style guide.
- Comments in this codebase explain *why* a non-obvious choice was made (usually a bug it prevents). Keep that habit; don't add narration.
- Add user-visible changes to `CHANGELOG.md` under `## Unreleased`.
- Cross-repo work (see `AGENTS.md`): siblings are `../bees-server` and `../bees-website`; read their `AGENTS.md` too, use the same branch name in each, keep server API changes backward-compatible, update server and desktop consumers together, never put server secrets here, and report status per repository. Do not commit unless explicitly asked.
