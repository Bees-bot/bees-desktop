# Software requirements

- Separate needs and constraints from implementation preferences.
- Accept “unsure” and recommend a default instead of forcing technical choices.
- Ask only questions whose answers materially change scope or architecture.
- Write observable acceptance criteria; avoid vague goals such as “fast” or “easy”.
- State assumptions explicitly and keep the first useful release smaller than the wish list.
